## NEXO-0008 — Pagination Architecture & Build Handoff (nexo-plan)

- Decision: adopt offset-based pagination (not cursor-based) for catalog
  entities. Admin CRUD views require page-number navigation; cursor pagination
  is more appropriate for infinite-scroll feeds. Both strategies remain
  available through the `paginate()` helper's generic design.
- Decision: hard limit of 100 items per page. Prevents abuse; CSV export will
  handle bulk retrieval.
- Decision: create reusable `src/common/pagination/` infrastructure with three
  files: `PaginatedQueryDto`, `PaginatedResponse<T>`, and `pagination.helper.ts`
  (runs `findMany` + `count` in parallel).
- Decision: install `class-validator` + `class-transformer` and register global
  `ValidationPipe` with `transform`, `whitelist`, and `forbidNonWhitelisted`.
- Decision: use clothing types as the tracer bullet — implement the full
  paginated stack for one entity first, validate the pattern, then replicate
  for the remaining 8 catalog entities.
- Decision: frontend uses TanStack Query `useQuery` with `keepPreviousData` for
  smooth pagination, a reusable `<Pagination />` component, and a generic
  `<CatalogTable<T>>` data table. No UI component library — all custom CSS.

## NEXO-0023 Phase 0 — Design Patterns & RequestLoggingInterceptor Handoff (nexo-plan)

- **Pregunta del usuario:** ¿Cuál es el mejor patrón de diseño para implementar
  un sistema de logging que permita visualizar cada endpoint entrante y cómo
  responde?
- **Análisis de patrones:** 4 patrones de diseño identificados y documentados
  para NestJS:
  - **NestJS Interceptor** (principal): AOP para cross-cutting concerns,
    envuelve cada request/response. Se ejecuta después de guards, por lo que
    tiene acceso a `req.user`. Superior a Middleware para logging.
  - **Observer**: SecurityLogger como sujeto; Winston/DB/Email como observadores
    suscritos por nivel de severidad.
  - **Chain of Responsibility**: Pipeline info→archivo, warn→+buffer,
    alert→+email inmediato.
  - **Exception Filter**: Complementa al interceptor capturando errores 500.

## NEXO-0027 — Image Optimization Pipeline: Sharp + WebP (nexo-plan)
 
 - **Usuario pregunta:** cómo optimizar fotos con Python y convertirlo en
   servicio. Se redirige a implementación directa en backend NestJS.
 - **Decisión:** Sharp (libvips) como procesador. WebP formato único de salida.
   Resize 2048px. Calidad adaptativa 82→60. Strip EXIF automático.
 - **Arquitectura:** extender módulo `media` existente con `ImageProcessorPort`
   (Strategy) + `SharpImageProcessorAdapter` + `UploadMediaUseCase` (orquestador).
   Mismo patrón hexagonal Port-Adapter que los módulos existentes.
 - **Decisiones técnicas:**
   - Sharp 4-10x más rápido que Jimp/Canvas. Streaming nativo, ~50MB RAM.
   - WebP -70% tamaño vs JPEG con calidad visual idéntica.
   - AVIF descartado (30x más lento en encoder, no viable en tiempo real).
   - `NoopImageProcessorAdapter` como fallback para CI/entornos sin sharp.
   - `IMAGE_PROCESSOR_PROVIDER=noop` para testing de HTTP sin imágenes reales.
 - **Plan creado:** `harness/control/plans/NEXO-0027-image-optimization.md`
 - **Handoff creado:** `harness/control/handoffs/HOFF-2026-07-07-image-optimization.md`
   — 14 archivos (8 nuevos, 5 modificados), 9 fases, 20+ tests.
 - **Live state actualizado:** `tasks.md` (NEXO-0027 active), `README.md`,
   `CURRENT.md`.
